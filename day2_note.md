# # Day2: Lsm

## 1. Что реализовано

Была создана система хранения на основе архитектуры **LSM**. Реализация затронула следующие компоненты:

-   **`internal/wal`**: Write-Ahead Log для обеспечения отказоустойчивости.
-   **`internal/sstable`**: Формат файла для хранения отсортированных, неизменяемых данных на диске (Sorted String Table) с поддержкой **разреженного индекса (Sparse Index)**.
-   **`internal/lsm`**: Ядро, которое управляет жизненным циклом данных: `Memtable` (на базе SkipList из первого дня), `Flush` (сброс Memtable в SSTable), `Compaction` (фоновое слияние SSTable) и восстановление после сбоя.
-   **`internal/kv/lsmstore`**: Адаптер, который предоставляет реализованный движок через стандартный интерфейс `kv.Store`, обеспечивая интеграцию с `kvtool`.

## 2. Инварианты и семантика

-   **Надежность**: Любая операция записи (`Put`, `Delete`) сначала фиксируется в WAL на диске, и только потом применяется в памяти. Это гарантирует, что даже при внезапном отключении питания данные не будут потеряны.
-   **Порядок чтения**: При поиске (`Get`) или сканировании (`Scan`) данные всегда просматриваются в строгом порядке приоритета: `Memtable` -> Новейший `SSTable` -> ... -> Старейший `SSTable`. Первая найденная версия ключа является актуальной.
-   **Удаления**: Операция `Delete` не удаляет данные физически, а записывает специальный маркер - надгробие. В моей реализации это запись с `nil`-значением. Этот маркер логически скрывает все предыдущие версии ключа. Физическое удаление происходит во время `Compaction`.

## 3. Принятые решения (и почему)

#### Формат WAL
Я выбрал бинарный формат с префиксом общей длины записи: `[TotalLen u32][Payload...]`.
-   **Причина**: Это обеспечивает надежное восстановление. Если сбой произойдет в середине записи, при следующем старте `Reader` прочитает `TotalLen`, попытается прочитать `Payload` и получит ошибку `io.ErrUnexpectedEOF`. Это позволяет безопасно отбросить последнюю битую запись и восстановить все целостные данные.

#### Формат SSTable
Файл состоит из трех частей: `[Data Blocks][Sparse Index][Footer]`.
-   **Причина**: Использование **разреженного индекса** - это оптимизация для чтения. Вместо того чтобы хранить смещение для каждого ключа, я индексирую только начало блока данных (каждые 4KB). При поиске это позволяет с помощью `io.ReaderAt` быстро прыгнуть в нужную область файла и сканировать только небольшой его фрагмент, а не весь файл целиком. Это снижает задержку чтения и требования к оперативной памяти.

#### Стратегия Compaction
Реализована стратегия, когда количество SSTable-файлов на диске превышает порог (в коде `> 3`), запускается фоновый процесс, который сливает все существующие SSTable в один новый, отбрасывая дубликаты и надгробия.
-   **Причина**: Стратегия проста в реализации и максимально эффективно освобождает место на диске.

1.  **При частой компактификации страдает в первую очередь Диск (запись) и CPU.** Диск - из-за высокого **Write Amplification**. CPU - потому что процесс слияния отсортированных файлов является вычислительно затратной операцией.
2.  **Для CDR-данных выгодно откладывать Compaction**, потому что это **write-heavy** нагрузка. Приоритет системы - максимально быстро принять и сохранить огромный поток входящих данных. Чтения редки, поэтому мы можем временно пожертвовать их скоростью (которая падает с ростом числа SSTable). Compaction можно запускать в периоды низкой нагрузки (например, ночью), чтобы не влиять на производительность записи в пиковые часы.

## 4. Контроль (как проверялось)

-   **Корректность**: Все тесты пройдены с помощью `make test-day2`. Добавлен дополнительный тест `TestCompaction_RemovesDuplicatesAndTombstones`, который проверяет, что слияние корректно удаляет дубликаты и надгробия.
-   **Отказоустойчивость**: Проведена симуляция сбоя с помощью `kvtool load -store lsm -dir ./lsm_test_db`. Процесс был прерван во время работы, после чего повторный запуск в той же директории прошел успешно, подтвердив, что данные были восстановлены из WAL.
-   **Производительность**: Для измерения производительности был создан бенчмарк `cdr-bench`, симулирующий нагрузку по данным из csv файла. Результаты показали высокую скорость записи:
    -   **`go run ./cmd/kvtool bench ...` -> 223,337 записей/сек**
    -   **`go run ./cmd/kvtool load ...` -> 345,740-462,463 оп/сек**
    Эти цифры демонстрируют главное преимущество LSM-архитектуры - эффективность последовательной записи.

## 5. Известные ограничения
-   Реализация не является потокобезопасной на 100%.
-   Стратегия Compaction очень проста и может приводить к большому Write Amplification.
-   Отсутствует кеширование блоков SSTable в памяти, что замедляет повторные чтения.
